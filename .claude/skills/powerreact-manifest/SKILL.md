# PowerReact manifests

A manifest is a report as data: which semantic model, which visuals where, what each one queries and how its result columns feed the component. PowerReact validates it, runs each visual's DAX (with the dashboard's cross-filters injected) and renders the Univerus web components. The elements stay presentational: **all data logic lives in the container** (`ManifestDashboard` / `ManifestVisual`).

```
manifest.json ─► validateManifest (Zod) ─► ManifestDashboard ─► ManifestVisual × N
                                                                   │  injectCrossFilters(dax, filters)  ◄── useFilterStore.crossFilters[manifest.id]
                                                                   │  useSemanticQuery (target = manifest.dataSource)          ▲
                                                                   ▼                                                           │
                                     POST /api/powerbi/query ─► mapRows(visual, rows) ─► <Univerus…> ── dataPointClick ───────┘
```

## Anatomy

```jsonc
{
  "$schema": "./manifest.schema.json",
  "schemaVersion": 1,
  "id": "asset-portfolio",                       // also the cross-filter scope: dashboards never filter each other
  "title": "Asset Portfolio (manifest)", "eyebrow": "Asset Management · manifest",
  "theme": "auto",                               // neoglass | nocturne | auto — applied once on load; the user's toggle wins after
  "dataSource": { "workspaceId": "<guid>", "semanticModelId": "<guid>" },
  "layout": { "columns": 12, "rowMinHeight": 120 },
  "visuals": [
    {
      "id": "groups",                            // lower-case, unique; also the element's visual-id and test-id prefix
      "component": "UniverusSpotlightBars",
      "grid": { "colSpan": 5, "rowSpan": 1 },
      "query": { "dax": "EVALUATE SUMMARIZECOLUMNS('asset_class_group'[Asset_Class_Group], \"Group Assets\", [Asset Count (All States)]) ORDER BY [Group Assets] DESC" },
      "fields": { "category": "'asset_class_group'[Asset_Class_Group]", "value": "[Group Assets]" },
      "crossFilter": { "field": "'asset_class_group'[Asset_Class_Group]", "emit": true, "respect": true },
      "props": { "title": "Assets by group", "subtitle": "…", "info": "…", "calc": "…", "secondary": "share-paren",
                 "export": { "csv": true, "xlsx": true, "fileName": "groups", "source": "visual" }, "focusMode": true, "tableView": true },
      "sample": [ { "asset_class_group[Asset_Class_Group]": "Core", "asset_class[Asset_Class]": "Buildings", "[Group Assets]": 1200 } ]
    }
  ]
}
```

- **`fields` map data, `props` only change presentation.** Field keys are result columns: `[Alias]` for what the query defines (`"Alias", <expression>`), `'table'[Column]` for group-by columns (executeQueries returns `table[Column]`; both spellings are accepted).
- Objects are **strict**: a misspelt key (`colspan`) is an error with its path, never silently ignored.
- `props.theme` pins one visual to a template; `props.format` is `{ style: integer | decimal | percent | currency | compact, decimals?, currency? }`.
- `export.source: "query"` exports the raw query rows instead of what the visual shows.

| `component` | `fields` | Notable `props` |
| :--- | :--- | :--- |
| `UniverusKpiCard` | `value`, `comparison?`, `meter?` (0..1) | `icon` (named), `caption`, `goodWhen`, `deltaLabel`, `meterLabel`, `meterDetail` |
| `UniverusKpiHero` | `value`, `comparison?`, `meter?`, `metrics?: [{label, field, format?}] (≤ 4)` | `unit`, `goodWhen`, `deltaLabel`, `meterLabel` |
| `UniverusSpotlightBars` · `UniverusRankingBars` · `UniverusDivergingBars` · `UniverusDonut` | `category`, `value` | spotlight: `topN`, `rank`, `secondary`, `selectedBadge` · ranking: `topN`, `order` · diverging: `negativeLabel`, `positiveLabel`, `maxRows` · donut: `centerLabel` |
| `UniverusBulletBars` | `category`, `actual`, `target` | `goodWhen: above|below`, `topN`, `targetLabel` |
| `UniverusTrendChart` | `category` (rows in time order: ORDER BY), `value`, `comparison?` | `seriesLabel`, `comparisonLabel`, `area`, `directLabels`, `chartHeight` |
| `UniverusIbcsVariance` | `category`, `actual`, `comparison` | `orientation`, `scenario`, `goodWhen`, `actualLabel`, `comparisonLabel`, `sort`, `topN`, `pctCap`, `decimals`, `chartHeight` |
| `UniverusDataTable` | `columns: [{field, label, kind?, format?, ratioField?, suffix?, tone?, emptyLabel?}]`, `rowKey?` | `paginated`, `pageSize` (10/25/50), `maxHeight`, `emptyMessage` |

Every visual also takes `title` (required), `subtitle`, `info`, `calc`, `format`, `export`, `focusMode`, `theme`; charts and the table add `tableView` (not the table) and `emptyMessage`. The schema file is the complete reference.

## DAX: trusted query, injected filters

- **A manifest's DAX is trusted input**, like a measure in the model: it comes from Univerus-Lens or the report author (AGENTS.md rule 3, exception). It must contain **exactly one top-level `EVALUATE`** (DEFINE / VAR / MEASURE blocks and `ORDER BY` / `START AT` are fine).
- **A clicked value is never trusted.** Filters are applied only by `injectCrossFilters`: a scanner that understands `"strings"`, `'quoted tables'`, `[brackets]` and comments splits the query and rewrites it as
  `<define>EVALUATE CALCULATETABLE(<table>, TREATAS({…}, 'table'[Column]), …)<order by>` — one `TREATAS` per column, values through `daxLiteral` (escaped strings, plain-decimal numbers, `TRUE()` / `FALSE()`), columns validated and normalised by `parseColumnRef`. No filters ⇒ the text is unchanged (same cache entry).
- **A visual is never filtered on its own column**: it keeps every category and highlights the selection (`selectedValue`), like Power BI's default. This holds for every visual whose `crossFilter.field` is that column (a donut on the same column as the clicked spotlight highlights too). `respect: false` ignores all filters; `emit: false` makes clicks inert.
- Same column and value again ⇒ the filter is removed; same column, other value ⇒ replaced; chips list them with **Reset all**. `resetAll()` (the /visuals Reset) clears every dashboard too.
- **Validate new DAX shapes against the real model once, read-only** (run the BFF and POST the query, plain and wrapped in `CALCULATETABLE(…, TREATAS(…))`), then teach the fake engine (`evaluateManifest` in `e2e/support/mockApi.ts`) any new measure or expression.

## Live, Sample and the BFF

- **Live**: each visual's DAX goes to `POST /api/powerbi/query` with `workspaceId` / `datasetId` from `dataSource`; the cache key is `["dax", kind, datasetId, DAX text]`. The BFF answers only datasets in `PBI_ALLOWED_DATASETS` (comma-separated ids; default: the configured `PBI_DATASET_ID`; `*` = any, development only) and returns **403** with a hint otherwise.
- **Sample**: no network. Each visual's `sample` rows (same shape as executeQueries rows) are filtered in the browser by the active cross-filters that name a column the rows carry, then aggregated to the visual's grain: measures are summed; ratios (`meter`, `ratioField`, percent formats) are averaged — an approximation for UI checks; Live is the truth. Ship samples at the finest grain you want to filter on (e.g. one row per class with its group).
- Changing Live / Sample remounts the dashboard (`key`), so hooks never change order.

## The harness (`/manifest-preview`)

Bundled manifests (from `public/manifests/index.json`), **Upload** (button or drag & drop, ≤ 2 MB), **Live / Sample**, a validation panel listing every issue with its path (`visuals[2].grid.colSpan: Too big…`), and **Schema** (downloads the JSON Schema). Grid: 12 columns by container query — every visual full width when narrow, KPIs (`colSpan ≤ 3`) two per row, then their own span from `@4xl`, every visual its `colSpan` from `@5xl`.

## Adding a component to the manifest

1. The element exists (powerreact-design-system §8).
2. `schema.ts`: a strict object in the discriminated union (`component` literal, `fields`, `props` with defaults).
3. `mapRows.ts`: a case returning the element's data props (and its entry in `MappedDataMap`); `crossFilters.ts`: how Sample mode aggregates it.
4. `registry.tsx`: the wrapper in `REGISTRY` and a `renderVisual` case (`satisfies` fails the build if a name is missing).
5. `npm run manifest:schema`; extend `schema.test.ts`, `mapRows.test.ts`, the fake engine and `e2e/manifest-preview.spec.ts`.

## Common mistakes

| Mistake | Effect | Fix |
| :--- | :--- | :--- |
| Two `EVALUATE` statements in a visual | Rejected by the schema (executeQueries would return only the first table) | One table per visual |
| `ORDER BY` inside the table expression | Invalid once wrapped in CALCULATETABLE | Top-level `ORDER BY` after the table (it stays outside the wrapper) |
| Building a filter with string templates in the container | DAX injection through a clicked label | `injectCrossFilters` only |
| `fields.value: "Group Assets"` | "Expected a result column like [Measure]" | `"[Group Assets]"` |
| A Trend without ORDER BY | Periods in engine order | `ORDER BY` the period (or its sort column) |
| A sample at the visual's grain only | Cross-filters cannot narrow it in Sample mode | Rows at the finest grain you filter on |
| Editing `manifest.schema.json` by hand | `schema.test.ts` fails (out of sync) | Change `schema.ts`, run `npm run manifest:schema` |
| A manifest pointing at another dataset | 403 "Dataset … is not allowed" | Add it to `PBI_ALLOWED_DATASETS` |
